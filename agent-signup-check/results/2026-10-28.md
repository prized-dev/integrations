Can an AI agent sign up for, fund and use a developer platform on its own? Seven checks, each read from public discovery documents with plain GET requests, run on 100 platforms agents use. The checker is one dependency-free Node file; anyone can run it on their own domain.

## The checks

Each check is pass, partly or fail. "Partly" means the platform has the thing in prose an agent can read, or in a shape the spec says a client must not use, but not in the machine-readable form the spec defines.

1. **auth.md** (`authmd`): Does /auth.md tell an agent how to register, in the shape of the auth.md spec? Spec: [WorkOS auth.md, AUTH.md v0.6.0](https://github.com/workos/auth.md/blob/main/AUTH.md).
2. **Protected resource metadata** (`prm`): Is there RFC 9728 metadata that names the authorization server? Spec: [RFC 9728, sections 2, 3 and 3.3](https://www.rfc-editor.org/rfc/rfc9728).
3. **Sign-up by API** (`register`): Can an agent find an API endpoint that creates an account, with no web form or CAPTCHA? Spec: [auth.md Step 1b (agent_auth in RFC 8414 metadata)](https://github.com/workos/auth.md/blob/main/AUTH.md#1b-fetch-the-authorization-server-metadata).
4. **Key works without a browser** (`challenge`): Does a signed-out API call get a 401 with a WWW-Authenticate challenge, not a login page or a bot wall? Spec: [RFC 9110 section 15.5.2; RFC 6750 section 3; RFC 9728 section 5.1](https://www.rfc-editor.org/rfc/rfc9110#section-15.5.2).
5. **Spend limits** (`limits`): Can an agent read the spend cap its key will have? Spec: [auth-md-spend-limits 0.1 (draft, Prized); draft-hardt-aauth-budgets-00](https://github.com/prized-dev/integrations/blob/auth-md-spend-limits/auth-md-spend-limits/README.md).
6. **Payment handoff** (`payment`): When money is needed, is there a machine-readable way for the agent to say so and hand over? Spec: [RFC 9110 section 15.5.3 (402); x402 v2 HTTP transport; draft-httpauth-payment; auth-md-spend-limits section 4](https://github.com/x402-foundation/x402/blob/main/specs/transports-v2/http.md).
7. **Docs in Markdown** (`markdown`): Is there an llms.txt an agent can read? Spec: [llms.txt (llmstxt.org)](https://llmstxt.org/).

## Method

- One run of `agent-signup-check.mjs` over the 100 platforms in `targets.json`, 4 platforms at a time, 300 ms between requests to the same platform.
- Read-only: GET requests only, to public documents meant for agents and to one documented API URL per platform without a key. No sign-ups, no POSTs, no forms, no credentials. At most 16 GETs per platform, redirect hops included (usually 7 to 9): `/auth.md`, `/llms.txt` (then one docs llms.txt when the root one is missing or has no H1), the API URL, protected resource metadata (the URL the 401 challenge names, then the well-known path on the site, then the one on the API host), authorization server metadata, `/.well-known/x402`, and, only when needed, the `agent_auth.skill` document and one made-up path to tell a real auth.md from a site that answers every path.
- https on port 443 only; every address a name resolves to must be public; 1 MB and 8 s per response; at most 4 redirects, each checked again.
- The API URL for each platform is one documented endpoint that needs a key (listed in 2026-10-28.json as `apiProbed`). GraphQL-only APIs (Railway, Linear) and platforms with no public REST API (Modal, Replit) were not probed, and Stripe's API was not called from this run's tooling; those rows are scored out of 6.
- "Partly" verdicts that rest on prose (auth.md or llms.txt text) quote the matching sentence in 2026-10-28.json, so a reader can judge it.
- A separate fact-check re-fetched every URL (all matched) and read every partial verdict and the main rows. Its fixes went into the checker before this run. 2 cell(s) the checker still gets wrong were corrected by hand, each marked "Corrected after review" in 2026-10-28.json: xAI limits (partial to fail); Stripe payment (partial to fail).
- Two checks (spend limits, payment handoff) accept fields from auth-md-spend-limits, a draft extension Prized wrote, alongside the IETF AAuth budgets draft, x402 and the Payment HTTP authentication scheme. No platform, Prized included, passed either check through the Prized draft's fields.
- Raw responses (status, headers, body) for every request are kept as evidence, one file per request: [evidence/](../evidence) at the commit that added this run.
- Limits: a check sees what a platform publishes, not what its sign-up does after a POST. A platform can let agents in through a CLI or an SDK that no public document describes; it scores lower here. Results change when platforms change their files; this is one dated run.

## What surprised us

1. **The top score went to a phone company.** Telnyx passes 6 of 7. Its auth.md registers agents at `POST https://api.telnyx.com/v2/bot_signup`, anonymously or with the person's email; its API's 401 points to RFC 9728 metadata; and `https://telnyx.com/.well-known/x402` sells chat completions per call in USDC, with no key and no sign-up. It misses only spend limits. No sandbox, hosting or LLM platform scored higher.
2. **Nobody publishes a spend cap an agent can read.** 0 of 100. 7 describe limits in prose an agent could find (Anthropic, Apify, Fireworks AI, Groq, Modal, NanoGPT, OpenRouter). NanoGPT's comes closest: its key handoff lets the asking app set a USD limit per day, week or month. None puts the cap where a client can read it before it signs up.
3. **Paying without an account is real, and rare.** 2 of 100 have a machine-readable way to pay: Telnyx's x402 manifest, and Financial Datasets, whose API answers a keyless call with `402` and an x402 `PAYMENT-REQUIRED` header ("Send an X-API-KEY header, or pay per call with x402"). 9 more describe a payment path in prose (Prized, Boat, Apify, Browser Use, Fireworks AI, NanoGPT, Orthogonal, Parallel, Tavily).
4. **Most APIs skip a rule HTTP has had since 1999.** RFC 9110 (and RFC 2616 before it) says a 401 MUST carry a `WWW-Authenticate` header. 68 of the 95 APIs we probed send a 401 without one, among them Anthropic, GitHub, E2B, Daytona and Supabase; 8 more answer 403, 400 or 422 with no challenge. 8 use the header to point an agent at their metadata (RFC 9728 section 5.1): Telnyx, Firecrawl, Kernel, Polar, Prized, Boat, Neon, PostHog.
5. **Protected resource metadata exists mostly because MCP needs it.** 10 of the 14 platforms whose metadata we could not count as valid publish one that describes an MCP server (resource `.../mcp`) at a location RFC 9728 section 3.3 says a client must not use for it.
6. **The file for agents is not always open to agents.** Perplexity, GitLab (after a redirect to its sign-in page) and CodeSandbox answer `/auth.md` with a Cloudflare bot challenge to a plain client. Sentry answers every path, `/auth.md` included, with the same Markdown page. Supabase's `/auth.md` is the Markdown version of its Auth product page.
7. **Sign-up with no person at all exists, mostly outside the metadata.** Telnyx, Polar, Boat and Neon (claimable databases) declare anonymous registration in `agent_auth` metadata a client can find. Clerk (accountless applications), Cloudinary (claimable clouds), Autumn (`agent.provision`) and WorkOS (one-shot environments) describe the same thing in auth.md prose only.
8. **5 platforms publish an auth.md to say no.** Fly.io, Loops, Resend, Apify, Cloudflare each serve an auth.md that tells agents they cannot register yet, and points them to what works today.

## Prized's own result

5 of 7, tied with 3 others behind Telnyx. Fails: Spend limits. Partly: Payment handoff.
- Spend limits: Prized publishes no spend cap. Per-key caps are built and in review; until they ship there is nothing to declare.
- Payment handoff: when credit runs out the API answers `409 insufficient_balance`, and auth.md tells the agent to send its person `billing_url`. That counts as partly. There is no `402` and nothing machine-readable.
- The `billing_url` / `billing_required` patterns were added to the payment check after reading Prized's and Boat's auth.md during the fact-check. They apply to every platform; Boat also matched them.

## Against an outside scanner

On the 37 platforms that Cloudflare's isitagentready.com also scanned (Oct 27 and 28), the auth.md pass/fail verdicts agree on 36 (NanoGPT: Cloudflare pass, here partly, because its auth.md documents OAuth and device login rather than a registration endpoint). Protected resource metadata agrees on 32; the 5 differences (Kernel, Firecrawl, Neon, Supabase, Resend) are platforms whose metadata sits on the API host or behind the API's 401, which this checker follows (RFC 9728 section 5, auth.md Step 1) and Cloudflare's scan of the site root does not.
