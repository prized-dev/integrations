# Method

How the agent sign-up check reads a platform, how the 100 were chosen, and what the results can and can't show. The code is [`agent-signup-check.mjs`](agent-signup-check.mjs); where this page and the code disagree, the code is right and this page is a bug.

## The platforms

[`targets.json`](targets.json) lists 100 developer platforms that AI agents sign up for or call, in eight categories: sandboxes and compute (28), LLM APIs (20), email, phone and messaging (11), browsers and scraping (10), search and data (9), databases and backend (8), dev tools (8), payments and billing (6). Prized picked them. Sandboxes and compute is the largest group because it is Prized's own market: Prized and the platforms it competes with are all in it.

For each platform the list names one documented API URL that needs a key (`api`; listed as `apiProbed` in the results), and, where the docs live elsewhere, the docs llms.txt (`docs`). Five platforms have no API probe and are scored out of six: GraphQL-only APIs (Railway, Linear), platforms with no public REST API (Modal, Replit), and Stripe, whose API the tooling that made the first run was not allowed to call. For the two GraphQL platforms the list still names the API URL: it is never requested, but its host is read for the metadata in steps 3 and 4 below. No API host is read for the other three.

## The requests

GET only, with `Accept` set for what is expected (Markdown, JSON). In order, stopping early where a step has nothing to follow:

1. `https://<domain>/auth.md`, `https://<domain>/llms.txt` and the API URL, signed out.
2. A second llms.txt (the docs one, or `/docs/llms.txt`) when the root one is missing, doesn't start with an H1, or was redirected to a page that is not an llms.txt and that the site also serves for `/auth.md` (a landing page that answers both paths is not an llms.txt).
3. Protected resource metadata (RFC 9728): the URL the API's `401` names in `resource_metadata`, then `/.well-known/oauth-protected-resource` on the site, then the same path on the API host, stopping at the first one a client may use. Metadata reached through the `401` may be used when the probed API URL is its `resource` or sits under it; metadata from a well-known path, when its `resource` is the one that path was built from (RFC 9728 section 3.1), counting the URL a redirect landed on. When none may be used, the verdict rests on the first of them that answered with JSON, and its reason says why a client may not use it.
4. Authorization server metadata (RFC 8414) for the first authorization server that usable metadata names, else `https://<domain>/.well-known/oauth-authorization-server`, then the same path on the API host when the site has none.
5. When `/auth.md` is missing, the auth.md that `agent_auth.skill` points to.
6. When `/auth.md` is Markdown but not in the spec's shape, one made-up path (`/agent-signup-check-no-such-page.md`) to tell a real auth.md from a site that answers every path with the same page.
7. x402 discovery: the `/.well-known/x402` URL the platform's auth.md or llms.txt names on its own site, else `https://<domain>/.well-known/x402`.

At most 24 GET requests per check of a platform, redirect hops included. Most platforms take 7 to 9 requests; one whose site redirects every path takes up to twice as many GETs. A weekly run checks a platform once more, alone, when a request got no answer: a network failure, a server error (HTTP 5xx), HTTP 429 or a bot challenge. Of the two checks it keeps the one that read more, and the diff records what both got. https on port 443 only; every address a name resolves to must be public, checked again on each connection and redirect; at most 4 redirects; 1 MB and 8 seconds per response. A run does 4 platforms at a time with 300 ms between requests to the same platform.

## The verdicts

Pass, partly or fail, per check; the README has the rule for each. Prose verdicts (a partly that rests on auth.md or llms.txt text) quote the sentence that matched. Rows are ranked by checks passed; ties share a rank and are listed by name; partly never breaks a tie. "Who acts at sign-up" comes from the identity types in `agent_auth` metadata, or, marked as such, from prose.

**Not read.** A fail says a platform lacks something, and that is only known when every file the check reads was read. So a check that would be a fail is published as "not read on <date>", with what the URL answered, when a request for one of its files got no answer: a network failure that could pass (a timeout, a reset), a server error (HTTP 5xx), HTTP 429, a bot challenge on the file's own path, or this checker's own request cap. Not read is neither a pass nor a fail. The check still counts in the row's seven (or six), so a row reads "2 of 7, 1 not read", and the verdict the checker would otherwise have given is kept beside it in the results (`was`, `wasReason`).

Each check answers only for the files it reads itself: `/auth.md` for auth.md; the metadata documents for protected resource metadata, sign-up by API and spend limits; the API's answer, x402 discovery and the authorization server's metadata for payment handoff; llms.txt for docs in Markdown. One URL that fails does not blank the checks that never read it. A partly rests on something that was read, so it stays a partly, and its reason names the file that was not read. Sign-up by API, spend limits and payment handoff also look in the prose of auth.md and llms.txt; when only that prose went unread and the check's own files all answered, the check stays a fail and its reason says which file was not read.

Everything else is the platform's answer and is scored: 404 and 410, a plain 403 or 401, an HTML page, a host that does not exist or has a certificate that cannot be trusted, and a redirect to a different page such as a sign-in page, even when that page then shows a challenge. A pass is never changed to not read. In a weekly run the platform has been asked twice by then, except where the checker's own cap stopped the request.

## Review and corrections

Before the first publication a separate fact-check re-fetched every URL (all matched what the run saw) and read every partial verdict and the top rows. What it found was fixed in the checker, and the run was repeated. Two cells the checker still reads wrong were corrected by hand: xAI's spend limits (its llms.txt matches on a consumer X subscription page, not the API) and Stripe's payment handoff (its llms.txt describes payment products Stripe sells, not a way for an agent to pay Stripe). Each is marked "Corrected after review" in its reason, with the checker's own verdict beside it, and each applies only while the checker still sees the same match on the same URL: if the page changes, the checker's verdict stands and the weekly diff lists the correction as stale.

As an outside check, on the 37 platforms that Cloudflare's isitagentready.com also scanned (October 27 and 28, 2026), the auth.md pass and fail verdicts agreed on 36. NanoGPT is the difference: Cloudflare passes it, this check says partly, because its auth.md documents OAuth and device login rather than a registration endpoint. Protected resource metadata agreed on 32; the 5 differences are platforms whose metadata sits on the API host or behind the API's `401`, which this checker follows (RFC 9728 section 5) and a scan of the site root does not.

## Prized's part

Prized wrote this checker, picked the platforms, and wrote auth-md-spend-limits, a draft extension that the spend limits and payment handoff checks accept alongside the AAuth budgets Internet-Draft (draft-hardt-aauth-budgets-00, an individual submission), x402 and the `Payment` HTTP authentication scheme. Prized is in the list, scored by the same code, and sorted with everyone else. In the runs of 2026-11-07 and 2026-11-12 no platform, Prized included, passed either check through the Prized draft's fields. A verdict that rests on them names `agent_auth.billing` in its reason, so each run's results show which platforms do, Prized among them. The `billing_url` and `billing_required` prose patterns were added to the payment check after reading Prized's and Boat's auth.md during the review; they apply to every platform.

## Limits

- A check sees what a platform publishes, not what its sign-up does after a POST. A platform that lets agents in through a CLI or an SDK it never describes in a public file scores lower here than it would in use.
- One API URL per platform. A platform whose other endpoints answer differently is scored on the one listed.
- An MCP server's host is read only when the site's or the API host's own well-known path redirects there, or the API's `401` points there; a host named only in auth.md or llms.txt is not requested. Netlify, Cloudinary and Render, among others, publish protected resource metadata for their MCP servers on separate hosts, so they fail this check. Exa and Loops redirect their site's well-known path to their MCP server's metadata, which is followed and passes. Apify and Fly.io, among others, serve metadata on their site whose `resource` is their MCP server; RFC 9728 section 3.3 says a client must not use it there, so this check says partly.
- A file behind a bot wall is not read, and since 0.2.5 it is not scored as a fail (earlier versions counted a bot wall against the platform). A plain client could not read the file that day, and an agent with a plain client could not either; whether the file exists is not known, and the same URL can answer with a challenge in one run and without one in the next. The row names the URL, what it answered and the date. One check is different: the 401 check asks whether the API turns a signed-out call away with a challenge an agent can parse, so a bot wall in front of the API itself is still a fail there.
- A server error is not read either. A platform whose file answers HTTP 500 for a week shows "not read" for a week, not a fail and not a pass.
- A platform that can't be reached in a run (every request failed on the network or answered HTTP 429 or 5xx, twice) keeps its last row, marked as not checked with the date of the row kept, so a bad network day never reads as a regression.
- Results change when platforms change their files. Each run is dated, and the weekly diff says what moved.

## Versions

- 0.2.5 (2026-11-11). Three changes, found by running 0.2.4 on all 100 platforms twice on 2026-11-11. (1) Not read: a check whose deciding request got no answer is no longer a fail (see "Not read" above); a weekly run now asks again after a server error, a 429 or a bot challenge, not only after a network failure. (2) The request cap goes from 16 to 24 GETs: 0.2.4 added a request on 64 platforms and kept the cap, so on three more platforms whose sites redirect every path the last request, x402 discovery, was no longer answered (four with Coinbase Developer Platform, whose x402 request the cap had stopped since 0.2.2). (3) A page that a site redirects both `/llms.txt` and `/auth.md` to is not an llms.txt, and the docs llms.txt is then read. Scored again from the 2026-11-07 responses plus one file 0.2.5 newly reads (`docs.cdp.coinbase.com/llms.txt`, fetched 2026-11-11), nine cells in four rows read "not read" where they read "fail": six on CodeSandbox (a bot challenge on every path of its site), auth.md on OpenAI and on Perplexity (a bot challenge on `/auth.md`), and docs in Markdown on Deno Deploy (HTTP 500 from its docs host). Nine more fails on those three rows keep their verdict and now say which file was not read. Coinbase Developer Platform's docs in Markdown still passes, now read from its docs llms.txt and no longer from its landing page, and its payment handoff goes from fail to partly: that file mentions x402 (its x402 request, which the old cap stopped, was not sent again for this re-score). No score, rank or total changes. 0.2.5 made the 2026-11-12 run.
